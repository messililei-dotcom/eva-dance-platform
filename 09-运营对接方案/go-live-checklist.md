## 一、上线前总说明

### 1.1 上线原则
1. **数据安全第一** — 任何操作不得破坏生产数据
2. **先验证后上线** — 本地测试→测试环境→生产环境，逐级推进
3. **可回滚** — 上线前必须确认回滚方案就绪
4. **分步上线** — 核心功能验证通过后再开放全部功能

### 4.2 回滚方案

#### 一级回滚（快速恢复 — 30分钟内）

**适用场景：** 数据库迁移失败、核心功能不可用、大面积用户无法访问

**回滚步骤：**

```
1. 停服（关闭新系统服务）
   → sudo pm2 stop 新系统服务名

2. 恢复数据库
   → cp 备份目录/dance.db 新系统目录/server/
   → 验证数据库完整（sqlite3 dance.db .tables）

3. 恢复代码（如需）
   → git checkout 部署前tag
   → npm install && npm run build

4. 切换Nginx路由回旧服务
   → 修改nginx配置，恢复旧域名指向旧系统

5. 重启服务
   → sudo pm2 restart 旧系统服务名

6. 验证
   → 确认旧系统正常访问
   → 确认数据无丢失

7. 通知全员
   → 群内通知：系统已回滚至旧版本
```

**回滚条件：**
- 新增订单<10笔（迁移后新订单少，损失可控）
- 回滚时间<30分钟
- 有完整备份可恢复

#### 二级回滚（数据修复 — 2小时内）

**适用场景：** 部分数据错误、单个模块功能异常、不影响核心业务

**回滚步骤：**

```
1. 隔离问题模块（如仅支付模块异常）
   → 先关闭该模块功能
   → 旧系统对应模块继续服务

2. 修复数据
   → 从备份中提取正确的数据
   → 使用SQL脚本增量修复

3. 代码hotfix
   → 修改bug后重新部署
   → 不影响其他模块运行

4. 验证
   → 问题模块恢复
   → 不影响其他已运行数据
```

**回滚条件：**
- 数据错误范围可控
- 可以增量修复无需全量回退
- 新订单数据可用

#### 三级回滚（数据补录 — 24小时内）

**适用场景：** 少量数据迁移遗漏、配置错误、显示问题

**处理步骤：**

```
1. 记录遗漏数据清单
2. 手工补录到新系统
3. 验证补录数据完整
4. 如影响客户 → 主动联系说明
```

**处理条件：**
- 数据遗漏不影响核心业务流程
- 可快速手工补录
- 客户体验影响极小

### 4.3 回滚决策流程

```
发现上线问题
    │
    ├── 严重级别判断
    │   ├── 阻塞级（学员无法登录/支付失败/数据丢失）
    │   │   └── 立即启动一级回滚 → 通知李校长
    │   │
    │   ├── 严重级（单个模块功能异常/部分数据显示错误）
    │   │   └── 评估影响范围 → 二级回滚或hotfix
    │   │
    │   └── 轻微级（样式问题/文案错误/排序异常）
    │       └── 记录issue → 后续迭代修复
    │
    └── 回滚后
        ├── 验证旧系统正常运行
        ├── 记录问题原因
        └── 制定修复计划后重新上线
```
