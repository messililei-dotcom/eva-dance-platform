# 学员数据统一与多系统融合落地规则

**适用范围：** 学员管理系统、网课系统、官方网站  
**核心目标：** 线下课程、线上课程、成品舞视频课可以分模块管理，但学员身份必须统一，业务数据必须围绕同一个学员主档案沉淀。

---

## 一、系统职责边界

### 1. 学员管理系统

学员管理系统作为统一业务中台，负责所有真实业务数据。

它管理：

1. 学员主档案
2. 线下课程
3. 线下缴费和课时核销
4. 线上课程授权
5. 订单、授权、学习记录
6. 后台人员和操作日志

### 2. 网课系统

网课系统不单独维护一套学员。

它管理：

1. 线上课程专栏
2. 成品舞视频课
3. 视频素材
4. 课程小节
5. 学习进度
6. 课程访问授权

网课系统读写学员时，必须使用学员管理系统里的 `Member`。

### 3. 官方网站

官网主要用于宣传、展示和获客。

它负责：

1. 品牌宣传
2. 课程介绍
3. 报名入口
4. 登录入口
5. 跳转学习入口

官网不保存真实学员主数据。凡是报名、登录、购买、授权、学习相关操作，都调用统一业务 API。

---

## 二、统一身份规则

### 1. 统一主表

所有前台用户统一进入 `Member` 表。

```text
Member = 线下学员 + 网课学员 + 成品舞视频课学员 + 官网报名用户 + 购买用户
User   = 后台管理员 / 老师 / 运营人员
```

禁止再新增独立的 `Student`、`Customer`、`OnlineUser`、`WebsiteUser` 作为前台身份主表。

### 2. 统一唯一标识

手机号是当前阶段的前台身份唯一凭证。

落地规则：

1. `Member.phone` 必须保持唯一索引。
2. 官网报名时，按手机号查找或创建 `Member`。
3. 网课登录时，按手机号查找或创建 `Member`。
4. 后台新增学员时，如手机号已存在，应提示合并或进入已有学员档案。
5. 手机号预授权时，可以先写手机号，学员登录后再关联 `memberId`。

### 3. 学员合并规则

如果历史数据里出现重复学员，应以手机号为主合并。

优先保留：

1. 有真实缴费记录的 `Member`
2. 有课时核销记录的 `Member`
3. 有网课授权或学习进度的 `Member`
4. 创建时间更早、信息更完整的 `Member`

合并时需要把以下表的 `memberId` 一并迁移：

```text
Payment
ConsumeRecord
Certificate
CourseAuthorization
VideoProgress
CourseOrder / Order
CommissionRecord
DistributionRelation
```

## 三、课程数据融合规则

### 1. 课程类型分层

课程分为三类，但都围绕统一学员：

```text
线下课程       -> Course
线上课程专栏   -> CourseSeries
成品舞视频课   -> CourseSeries + OnlineCourse / CourseVideo
```

### 2. 线下课程

线下课程继续由学员管理系统管理。

核心表：

```text
Course
Payment
ConsumeRecord
```

典型流程：

```text
创建/选择 Member
  -> 创建线下课程缴费 Payment
  -> 上课后写入 ConsumeRecord
  -> 更新剩余课时
```

### 3. 线上课程和成品舞视频课

线上课程和成品舞视频课统一使用网课模块表。

核心表：

```text
CourseSeries
OnlineCourse
CourseVideo
Material
CourseAuthorization
VideoProgress
```

典型流程：

```text
创建/选择 Member
  -> 创建订单或后台授权
  -> 写入 CourseAuthorization
  -> 学员观看视频
  -> 写入 VideoProgress
```

## 四、交易与授权规则

### 1. 线下缴费和线上订单分开

`Payment` 继续承载线下课程缴费、课时、核销业务。

线上课、成品舞视频课、会员、分销商品应进入统一订单表。

当前网课脚本已有 `CourseOrder`，后续可以继续保留，也可以升级为更通用的 `Order + OrderItem`。

建议第一阶段：

```text
Payment     = 线下缴费和课时业务
CourseOrder = 网课和成品舞视频课购买订单
```

建议第二阶段：

```text
Order      = 全平台统一订单
OrderItem  = 订单明细
Payment    = 线下课缴费/核销业务记录
```

### 2. 授权是看课的唯一判断

学员能不能看线上课，不应该直接查订单，而应该查 `CourseAuthorization`。

授权来源包括：

1. 购买后自动授权
2. 后台手动授权
3. 手机号预授权
4. 线下购买后补录授权
5. 活动赠送授权

判断规则：

```text
已登录 Member
  -> 查 memberId 授权
  -> 查 phone 预授权
  -> 未过期且状态有效
  -> 允许访问课程
```

## 五、官网接入规则

官网可以保留本地展示配置，但所有业务动作必须走 API。

### 1. 可以本地配置的数据

```text
首页文案
品牌故事
宣传图片
课程展示卡片
老师介绍
活动介绍
```

### 2. 必须走统一 API 的数据

```text
报名提交
手机号登录
我的课程
订单创建
支付结果
课程授权
学习进度
分销绑定
```

官网报名流程：

```text
官网表单
  -> POST /api/public/enroll
  -> 学员管理系统按手机号查找/创建 Member
  -> 写入线索、报名或缴费待跟进记录
```

---

## 六、第一阶段落地顺序

第一阶段目标是先把学员身份和看课权限统一，不急着做完整商城。

建议顺序：

```text
1. 以学员管理系统数据库作为主库
2. 把网课 Phase 1/2 表合并进学员管理系统初始化逻辑
3. 保留 Member.phone 唯一索引
4. 给官网报名接口增加按手机号查找/创建 Member 的逻辑
5. 做手机号预授权和登录后自动关联
6. 做学员端“我的线下课 / 我的网课 / 我的成品舞”聚合页
7. 再接订单、支付、分销和会员
```

---

## 七、统一后的学员画像

统一后，一个学员档案应该能看到：

```text
基础信息：姓名、手机号、地区、来源
线下课程：报名课程、缴费记录、剩余课时、核销记录
线上课程：已购专栏、授权专栏、学习进度
成品舞视频课：已授权视频课、观看记录
证书认证：证书、等级、传承弟子信息
来源增长：官网报名、分享来源、邀请人
消费记录：线下缴费、线上订单、退款记录
```

这就是后续运营、复购、分销、会员体系的数据基础。

---

## 八、最终原则

```text
系统可以分，学员不能分。
课程可以分类型，身份必须统一。
官网负责获客，后台负责数据，网课负责交付。
所有业务最终都沉淀到同一个 Member。
```
