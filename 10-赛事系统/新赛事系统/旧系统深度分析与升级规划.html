1. 旧系统资产画像

旧系统由 Java 微服务后端、微信原生小程序、MySQL SQL 备份、用户/评委 Excel 清单组成。

资产盘点

后端

包含 `software-auth.jar`、`software-gateway.jar`、`software-modules-system.jar`、`software-modules-file.jar` 等服务包，配置来自 Nacos 风格的 `software_config.sql`。

小程序

`小程序mp-vote` 是微信原生小程序，名称偏“报名投票系统”，实际覆盖赛事展示、报名、评委打分、成绩查看、排行、用户中心。

数据

`software_cloud.sql` 是核心业务库，`产赛用户.xlsx` 与 `评委数据.xlsx` 是外部补充清单，已通过迁移脚本合并入新快照。

2. 业务流程还原

旧小程序虽然命名为报名投票，但真实业务已经形成一条完整赛事链路。

业务链路

赛事发布

后台配置赛事、海报、报名开关、城市、视频号和介绍。

选手报名

用户选择赛事与组别，填写节目、机构、老师、音乐、人数并支付。

组别编排

通过组别排序、出场顺序、评委组别关系组织现场比赛。

评委评分

评委绑定手机号或密钥后，对选手按评分规则提交分项分数。

成绩发布

选手可付费查看成绩，系统提供排行和历史记录。

3. 数据模型与保留策略

升级前最重要的是不丢数据。新系统应把旧字段原样保留，同时建立更清晰的业务实体。

数据治理
2033Excel 产赛用户
681按用户 ID 匹配 SQL
8Excel 用户未在 SQL 找到
256SQL + Excel 评委去重

保留原则

  • 旧 SQL 和 Excel 作为原始凭证，不覆盖、不删除。
  • 每条迁移数据保留 `legacy_id`、`legacy_table`、`source_file`。
  • 成绩、支付、报名状态类字段优先原样迁移，后续再做状态归一。
  • 手机号、OpenID、昵称等敏感字段只在授权角色可见。

实体重构

  • 赛事：由 `dfwq_competition` 升级为赛事项目、届次、赛程、素材。
  • 组别：由简单分组升级为组别、场次、赛制、评分规则。
  • 用户：拆分账户、选手身份、评委身份、主办方身份。
  • 评分：保留原始分项记录，并新增可审计的成绩计算结果。

4. 问题诊断

旧系统可支撑业务运转，但继续扩展会遇到架构、数据、运营和现场稳定性的瓶颈。

风险识别

架构风险

  • 微服务 jar 与配置备份存在，但源代码不完整，后续维护成本高。
  • 网关、认证、系统、文件模块耦合了旧环境地址和云资源配置。
  • 小程序接口是扁平接口名，缺少清晰版本、权限边界和错误规范。

数据风险

  • 用户、评委、选手关系混在 `dfwq_comps_user` 和 Excel 中，需要统一身份模型。
  • 组别多达 1700 条，依赖排序和 ID 关联，缺少赛程/场次层。
  • 评分记录量大，必须保证原始分、计算分、发布分三层可追溯。

运营风险

  • 报名、音乐、支付、出场顺序、成绩查看都在选手表内，运营筛选困难。
  • 评委授权由组别关系和密钥承载，缺少现场启停、锁定、异常复核。
  • 缺少赛事结束后的证书、奖项、素材、财务、数据分析闭环。

体验风险

  • 小程序页面已覆盖功能，但偏单点流程，现场大屏和后台协同不足。
  • 付费查看成绩、排行、评委评分之间需要更明确的状态提示。
  • 国际赛事包含中英文内容、海外手机号，数据格式需要更强兼容。

5. 产品定位与升级目标

AiwaRaks赛事管理平台不是单纯报名、评分、查成绩，而是连接赛事报名、选手管理、评委评分、证书发放、课程转化、会员沉淀、财务统计和活动复盘的一体化运营中枢。

产品目标

最优产品定位

不要把它做成“赛事报名系统”，而要做成“AiwaRaks赛事 + 学员 + 课程 + 会员 + 商业转化的一体化运营中枢”。旧系统沉淀的真实赛事、报名选手、评委和评分记录，是未来形成行业壁垒的数据资产。

完整赛事生命周期

从赛事创建、报名、审核、排赛、签到、评分、排行、证书、财务到复盘数据，全链路管理。

现场稳定与可控

评委授权、评分提交、成绩锁定、异常复核、大屏发布都可由主控台实时控制。

历史数据可追溯

旧数据迁移后可查询、可核验、可导出；评分计算保留原始记录与发布记录。

多角色协作

管理员、主办方、报名负责人、财务、评委、选手、观众拥有不同入口和权限。

专业后台界面

管理后台首页采用赛事运营看板形态，包含 KPI、今日赛事、报名趋势、状态分布、渠道分布、待办、最新报名和公告。

国际化能力

兼容海外手机号、多语言赛事介绍、国际城市、不同货币和跨区域赛事。

手机浏览优先

报名、评委评分、主控查看、成绩发布确认都必须适配手机浏览器，现场可不用电脑也能完成关键操作。

可扩展商业化

报名费、成绩查看费、证书、课程、电商、会员权益可与统一平台逐步打通。

6. AiwaRaks赛事管理平台结构

推荐采用“统一平台入口 + 赛事独立业务域 + 数据融合”的结构。统一平台提供账号、权限、支付、证书、消息等公共底座；赛事保持独立业务边界，承载报名、编排、评委评分、现场主控、成绩发布和大屏。

目标架构

统一平台入口与公共底座

所有管理人员从统一平台进入，复用统一登录、组织、角色权限、会员档案、订单支付、文件素材、证书、消息通知和操作日志。

统一登录 组织/角色 会员档案 订单支付 证书 消息通知 文件素材

赛事独立业务域

赛事不是统一平台里的普通页面，而是一个独立业务中心。它有自己的业务状态机、现场稳定性要求、评委授权矩阵、成绩计算规则和发布流程。

赛事管理后台 小程序报名端 评委评分端 现场主控台 大屏展示端 手机浏览优先 成绩引擎

数据库融合但按域隔离

赛事数据进入统一平台数据库，但使用 `event_*` 或 `competition_*` 前缀形成独立表域；通过外键关联统一账号、组织、订单、证书和文件，避免重复账号、重复支付和重复客户数据。

platform_users platform_orders platform_certificates event_events event_divisions event_scores

管理后台

赛事档案、组别赛制、报名审核、音乐审核、出场顺序、评委授权、成绩发布。

小程序选手端

赛事浏览、报名、缴费、音乐上传、报名记录、成绩查看、证书领取。

评委评分端

手机号/邀请码绑定、组别列表、选手评分、提交锁定、评分历史。

现场主控台

赛程推进、评分开关、异常提示、成绩复核、榜单发布、大屏控制。

大屏展示端

赛事主题页、当前选手、评分进度、排名、奖项名单、二维码入口。

数据与审计

旧数据迁移、重复检测、手机号异常、评分异常、操作日志、导入导出。

7. 新数据结构建议

用更清晰的实体关系承接旧表，同时保留旧 ID 便于追溯和回滚。数据进入统一平台数据库，但赛事表独立成域，公共能力引用平台表。

数据设计

平台公共表

承接统一账号、组织、会员、订单、支付、证书、文件、消息和操作日志。赛事系统只引用这些公共表，不重复建设一套账号和财务体系。

赛事业务表

赛事表使用 `event_*` 前缀，例如 `event_events`、`event_divisions`、`event_registrations`、`event_score_records`，保持业务边界清晰。

8. 接口与小程序升级计划

先保留旧接口兼容，再逐步切换到版本化 REST/API，降低一次性替换风险。新接口按平台、赛事、评委评分、成绩发布分组。

接口计划

兼容层

  • 保留 `getCompList`、`getComp`、`submitSignup`、`submitRating` 等旧接口名。
  • 旧小程序不立即重写，只把接口指向新服务兼容层。
  • 兼容层负责把旧字段映射到新实体，返回旧格式。

新接口

  • `/api/v1/platform/...`：账号、组织、权限、订单、文件、证书、消息。
  • `/api/v1/event/events`：赛事、海报、报名配置、发布归档。
  • `/api/v1/event/divisions`：组别、场次、评分规则。
  • `/api/v1/event/registrations`：报名、音乐、支付、审核。
  • `/api/v1/judging/...`：评委授权、选手列表、评分提交、漏评提醒。
  • `/api/v1/results/...`：成绩计算、锁定、发布、撤回、证书。

小程序端

保留轻量报名和成绩查询体验，增加报名进度、音乐状态、证书入口。

评委端

评分页减少干扰，重点保障授权清晰、选手切换快、提交反馈明确。

后台端

所有高风险操作记录日志，包括成绩重算、评分解锁、报名退款、榜单发布。

评分系统必须单独作为核心模块

评分系统不是普通 CRUD。它必须具备评委授权开关、组别评分锁定、单个选手评分状态、漏评分提醒、异常分预警、去最高最低分、复核后发布、发布后留痕和重新计算记录。旧系统已有 65248 条评分记录，新系统必须把原始分、计算分、发布分三层拆清楚。

10. 技术与安全架构

结合旧系统 Java 微服务资产，建议初期采用模块化单体或轻量服务化，避免一开始就恢复复杂微服务带来的运维成本。

工程架构

访问层

小程序端、H5 评委端、管理后台、现场主控台、大屏展示端统一接入 API Gateway，支持鉴权、限流、版本管理和日志追踪。

服务层

赛事服务、报名服务、评分服务、成绩服务、证书服务、订单服务、文件服务、消息服务按业务边界组织，先模块化再按压力拆分。

数据层

MySQL 承载核心业务，Redis 缓存当前赛事/评分/大屏状态，OSS 存储海报、音乐、证书和素材，审计日志独立留存。

角色与权限

  • 超级管理员：管理全平台所有数据和配置。
  • 平台运营：管理赛事、报名、内容、消息。
  • 主办方管理员：管理自己组织下的赛事。
  • 赛事负责人：管理指定赛事。
  • 报名负责人：管理报名、审核、音乐。
  • 财务人员：查看订单、支付、退款和收入统计。
  • 计分负责人：管理评分、复核和成绩发布。
  • 评委：只可对授权组别评分。
  • 选手：查看自己的报名、成绩和证书。

安全与稳定性

  • HTTPS 全站加密，JWT + RBAC 权限。
  • 手机号、OpenID、支付数据脱敏展示。
  • 成绩、支付、证书、高风险操作二次确认并写日志。
  • 防止接口重复提交，防止评委越权评分。
  • 评分接口优先保障，现场评分支持自动保存。
  • Redis 缓存当前赛事状态，大屏可手动刷新。
  • 重大赛事前提供演练模式和备份检查。

验收类型 验收标准
数据验收旧赛事、报名、评委、评分记录完整导入；每条迁移数据可追溯旧 ID；异常数据有清单。

9. 阶段路线图

建议分阶段建设，先保障历史数据和核心赛事流程，再扩展商业化和智能化能力。

实施计划
第 1 阶段

数据迁移与只读管理台

完成 SQL/Excel 迁移、数据核验、赛事/报名/评委/评分查询、导出和异常清单。当前已完成第一版 HTML 管理原型和迁移快照。

第 2 阶段

新赛事后台 MVP

把赛事入口挂入统一平台导航，复用平台登录、组织、角色、文件和订单能力；在赛事业务域内完成赛事、组别、报名、选手、音乐、评委、评分规则管理。

第 3 阶段

现场评分闭环

上线评委端、现场主控台、大屏、成绩计算、排名发布、漏评分提醒、异常分预警和复核锁定，保持现场评分逻辑独立稳定。

第 4 阶段

小程序报名端升级

旧小程序接口接入兼容层，新小程序逐步替换报名、支付、音乐上传、个人中心、成绩查询和证书领取，并与统一会员中心打通。

第 5 阶段

证书 + 财务 + 数据看板

成绩和奖项回流平台证书模块，报名订单进入统一财务；建立收入统计、报名统计、机构统计、老师统计和赛事复盘看板。

第 6 阶段

商业化增长

将赛事选手转化到课程、会员、电商、训练营和复训营，沉淀学员画像、机构/老师资源库和长期复购资产。

结论

旧系统的核心价值是已经沉淀了真实赛事、选手、评委与评分数据。升级重点不是推倒重来，而是以数据可追溯为底线，采用“统一平台入口 + 赛事独立业务域 + 数据融合”的方案：统一平台做账号、权限、支付、证书和会员底座，赛事系统做独立业务中心，数据库融合但边界清楚。
